## Scope

This proof exercises the merged v0.7.4.3 implementation with deterministic,
secret-free fixture bytes in an isolated temporary directory. It uses the real
Coding Pack Runtime read plan and manifest, a real SQLite database, the pinned
managed Python distribution, the real AgentFuse bridge and policy, and the
production macOS native writer. The positive case uses no decision or
filesystem mock.

Run:

```bash
./validation/run_kerniq_v0_7_4_4_native_export_proof.sh
```

builds a fresh managed profile, creates a fresh temporary proof root, executes
the ignored controlled Rust proof, writes the redacted evidence artifact, and
removes the proof root. Download cache contents and temporary project,
destination, SQLite, and exported bundle data are not committed.

## Negative And Uncertainty Proofs

| Case | Result |
| --- | --- |
| Existing final target | Untouched; no START and no staging residue |
| Source drift | `coding_pack_source_changed_before_export`; no START and zero destination writes |
| Destination unavailable | Failed closed; no unsafe or redirected write |
| Destination path replacement | Replacement path received zero writes; retained opened object received the target |
| Policy block/deny | Real invalid exact-request mutation returned `block`; separately, strict durable deny state prevented export and produced zero writes |
| Completion persistence fault | Target retained, state `export_started`, no completed/interrupted event, no automatic retry |
| Post-promotion sync fault | Target retained, state `export_started`, no completed/interrupted event, no automatic retry |

The frozen export policy allows every exact valid trusted request. Therefore
the policy-negative proof does not claim one valid-request end-to-end deny. It
proves the real policy blocks a controlled invalid request and separately
proves the strict store's durable deny-to-zero-write boundary. Changing the
frozen policy merely to manufacture another deny condition is outside this
proof.

The two uncertainty cases are explicit test-only fault injections. They prove
the production state mapping and native target-retention behavior; they do not
claim that the production SQLite store or physical disk actually failed.
